# How the app should behave in a person's hand

## The first minute and the hundredth project

Someone picks a photo, straightens it, covers a house number, adds a caption and saves a copy. They should recognize their photo throughout. They should be able to point at the object they are editing, find the primary action with a thumb, see an immediate response and recognize their finished copy in another viewer. They can tell what Save project will preserve and what Export image will flatten. A professional then opens the project again, adjusts only the caption, exports a second version, and still has both the untouched source and an editable project.

This describes two different skill levels using the same layout. Keep the familiar first actions where the owner already knows them. Reveal detailed parameters within the tool that uses them. A selected brush shows size, softness and strength. A selected tile identifies which photo is active. Selection-dependent controls explain what object to select when the prerequisite is missing. The canvas should retain working space when the keyboard, tool strip or system gesture insets appear. Hiding controls to work on a corner should leave an obvious route to show them again. A tool's preview should appear on the user's image as soon as that tool can give meaningful feedback. A selection outline has a different job from the rendered effect.

For a first-use observation, give a person unfamiliar with the app an outcome: “Crop this to a square, hide this address and save a copy.” Hand over the phone without identifying which buttons to press. Note the first wrong tap, retries at the edge, prompts interpreted backwards, and where they look for their saved file. Repeat with a practiced user on a layered retouch. Fix the first obstacle and repeat both journeys. The design target is that a young first-time user can succeed. Recruiting a minor is unnecessary to run the initial readability and discoverability checks.

## Which object owns this action?

| Action in the person's hands | Working state | What persists |
|---|---|---|
| Drag a slider or draw a stroke | A changing preview owned by one document, tool and target | Its final value or one stroke at commit. Undo returns to the pre-gesture state. Cancel returns precisely to that state. |
| Zoom, pan, hide controls, inspect Before | A viewing decision. Before is a comparison that can be exited. | Edited pixels and authored history stay intact. If the view is restored later it is restored as a view. |
| Open Pro from Regular with an edited photo | Yes gives Pro the rendered crop, orientation and current edits. No opens an empty Pro editor. The user can open media there or return to the Regular draft. Canceling the Pro picker returns to the same Pro screen. | Regular keeps its own document, undo state and source. Pro owns a fresh document. A later Pro export can enter Regular as another photo. |
| Select a layer, a tile, a timeline clip or a GIF frame | A stable identity identifies the target, including where the same source appears twice. | Reorder, undo, delayed decode and picker return act on the intended identity. A missing selected source gives the user a relink/recovery path. |
| Save a project | A new version of an editable recipe with source references, asset identities and a working baseline | Complete recoverable data; edits with older file formats still render correctly on reopen. A failed new save keeps the previous valid save available. |
| Export media | A snapshot of project content, settings and output destination for this job | A fully encoded asset matching that snapshot. A subsequent edit belongs to the next export. The original remains recoverable and unchanged. |

A useful implementation model has four boundaries: source media, editable document, current gesture, and derived media such as proxy frames or thumbnails. If they already exist in the repository, reuse them. A cache can be discarded. An unfinished stroke generally can be canceled. A saved mask from an older project holds user work even when there is no longer a menu to author it. A migration that treats all three the same will lose data. Keep stable identities when changing storage representation. In particular, a slot index is a location, not the identity of a layer.

## A gesture from touch-down to the next screen

Capture the intended target from the first useful contact. In a small crop box, large touch regions compete. Resolve corner, edge and interior hits using distance, intended geometry and a deterministic tie rule. Run exact-midpoint, interior and near-corner cases. Preserve the anchor when the finger crosses the slop threshold. Handle display density, letterbox space, zoom and system insets when translating the coordinate into the source. Test small boxes where physically disjoint 48 dp target areas are geometrically impossible; make the competition predictable. A finger-sized target need not change the visual design.

During a heavy gesture the user needs two kinds of response. First acknowledge the touch, then present the actual changed content. A thumb knob that moves immediately above frozen media satisfies only the first. Measure event-to-visible-content latency. During long render, codec or file work the UI can still respond to release, navigation and cancellation. Associate asynchronous results with source, document revision and edit generation. A result for an old generation completing late cannot reclaim the visible screen or overwrite a newer cache entry. Introduce grouping, cancellation or buffering where traces show they help. Confirm that caches release their resources after exit and repeated switching.

Make hidden controls reachable with TalkBack. Focus should return to the initiating control after a sheet or picker closes. Give nonvisual controls a name, target and value; a slider needs an adjustable role and a usable alternative to tiny movements. Test a larger font, landscape, both light and dark image content and both system navigation styles. A checkerboard is a view of transparency and must stay out of a transparent PNG. Confirm the edit while checking these conditions; a static accessibility scan cannot reveal if Back abandons it. [Android accessibility guidance](https://developer.android.com/guide/topics/ui/accessibility/apps)

## Back should answer “Where was I one step ago?”

| Start | Committed Back | Canceled or interrupted gesture |
|---|---|---|
| System picker or text keyboard is active | Let the system component handle its own dismissal. Return to the same editor and target. A remaining text dialog can then use its normal commit/cancel behavior. | Keep the same picker/text draft and insertion point where the platform supports it. |
| Dialog, sheet or expanded controls sit over a canvas | Dismiss the foremost transient surface once and restore focus. | Keep the same surface and current values. |
| In-progress Pro tool draft | At the established Back point, leave the draft and restore the prior committed document. | Keep editing the same target. No accidental stroke or undo entry. |
| Inside a tile editor, project subview or secondary workspace | Return one route to the previous working context, retaining selection, edits and history. | Keep route and history unchanged. A fast second Back is handled as its own event against the resulting state. |
| Dirty document or active save | Follow the established retain/save/discard handling. A recoverable draft can return the user quickly. Where data would be lost, offer a clear choice. Track a provider write through its safe cancellation boundary. | Leaving the visible screen does not turn a partial file into a successful export. |
| Actual app root | Normal Android Back behavior is appropriate once the person truly reaches the root and unsaved-work handling is complete. | Return to the same root. |

Exercise committed and canceled predictive gestures from both edges on an actual gesture-navigation phone; also exercise three-button Back and the keyboard. Launch a picker, rotate, return with a grant, cancel once, then retry. Dispatching through AndroidX covers the app's navigation decision; only a real system gesture can demonstrate edge ownership, predictive preview and OEM behavior. [Android predictive Back](https://developer.android.com/guide/navigation/custom-back/predictive-back-gesture)

## Save, recovery and user-owned media

Keep saved and in-progress documents distinct. Persist the user's editable decisions and enough information to resolve each source. Large bitmaps, clip buffers and codec instances can be rebuilt. Android's saved-state mechanisms suit small reconstruction keys; a durable local project/draft is the place for substantive work. Restore that work on cold re-entry as well as configuration change. Treat a process killed after backgrounding differently from a user explicitly deleting current work. [Android state saving](https://developer.android.com/topic/libraries/architecture/saving-states)

A robust save keeps the last good revision until the replacement is complete. Stage a write where the chosen storage system permits it, validate length/structure and referenced assets, and publish success only after closing the output successfully. A document provider may offer no atomic rename or durable URI guarantee. In that case retain the local recovery copy, report a specific failed destination and allow retry to a new one. Prevent a second Save tap from publishing two unwanted results. An external URI grant can be revoked or the file moved; offer a relink with an identity check before applying old transforms to a replacement. [Android documents and other files](https://developer.android.com/training/data-storage/shared/documents-files)

Rehearse three failures deliberately. Kill the process just before publishing the new project version and reopen the prior save. Revoke a grant after two collage tiles reference the same source, relink once in an explicit scope and verify both independent edits. Fill the destination while finalizing a GIF and retry into a different folder. Inspect the actual provider listing, project file and externally opened result after each run. Preserve the source bytes, previous valid output and named projects throughout. A success snackbar proves only what the UI reported.

## Product boundaries that guide engineering choices

The product is an Android-first, local editor with a one-time purchase target of $2.99. Edits, imported audio, photos and documents stay local. Account services, runtime AI, telemetry, ads, subscriptions, purchases of tool packs and watermarks are outside the agreed product. Professional results such as replacing a background or refining a silhouette can be achieved with selections, edge refinement, brushes, masks and deformation tools. Publishing original sticker assets created during development and integrating a model that processes a user's photo at runtime are separate product decisions. Maintain an origin and commercial-use record for assets and dependencies; the actual license and distribution terms govern each inclusion.

The final launch experience begins **after all five workspaces have been built and tested**. At first open present the welcome and English/Spanish language choice, show the applicable agreements, capture the chosen language and accepted document versions locally, and unlock the editor after agreement. Define decline, later review and re-consent behavior when the final policies are written against the actual shipped app. Validate the full product in both languages, including errors, plural forms, menu widths, accessibility names and offline first use. Work on these screens and translations belongs to the final phase. Earlier feature engineering can preserve a clean separation between UI text and media data without diverting into a localization project.
