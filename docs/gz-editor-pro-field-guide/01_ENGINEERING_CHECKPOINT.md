## What the GIF measurements actually show

Measured in the original per-case logcats alongside the XML results. The source is a synthetic 1080 × 1920 portrait video. The edited output is **180 × 320, 88 frames, 2.950 seconds**. Treating input resolution as output resolution would grossly overstate the amount of encoding work tested.

| Observation | Android 10, API 29 | Android 15, API 35 |
|---|---:|---:|
| Main #223, portrait Save GIF | 77.091 s | 39.102 s |
| PR #20 run #225, portrait Save GIF | 4.874 s | 6.649 s |
| Main #230, portrait Save GIF | 5.128 s | 6.210 s |
| #225, time to finish staging the portrait export | 4.750 s | 6.468 s |
| #223, time for the edited playback test to observe five distinct visible samples | 3.070 s | 3.203 s |
| #225, same five-sample observation | 2.633 s | 5.098 s |
| #230, same five-sample observation | 2.397 s | 4.454 s |
| #225, 720p60 long-GOP normalization fixture, timestamp-seek reference → production export to 180 × 320, 80 frames | 22.574 s → 2.697 s | 18.497 s → 2.828 s |

**How to use these numbers.** The portrait Save operation improved substantially across runs. Both timers start at Save. The old timer includes reopening and reading file metadata, whereas the new timer stops when the saved-GIF action becomes visible. Reading the saved bytes in the earlier test was distinct from reopening the GIF in the editor. The 720p60 reference and production pair runs on the same emulator and is cleaner evidence about decoder throughput. These are individual CI samples. The five-image measurement includes the test’s observation cadence and cannot establish a frame rate or sustained responsiveness. The API 35 five-image time increased in this run. Track playback separately from export with a visible frame signature, a time series and multiple trials.
