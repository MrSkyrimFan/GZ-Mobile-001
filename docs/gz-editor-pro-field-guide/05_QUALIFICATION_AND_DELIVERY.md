# How to decide when the job is done

## A useful test can contradict its author

The owner's problem was “once I edit, I get zero playback.” A log saying “playing” would pass on the broken experience. Five distinct pictures establish that some visible motion returned. They do not answer whether the middle froze, whether Play reached the end on time, whether repeated edits jammed it again, or whether the reopened file played the same edit. These are separately testable claims. Choose the smallest observation that can distinguish the broken behavior from the one the user asked for.

For each repair, retain the ordinary route into the problem, a source or fixture identity, the exact edit sequence, the previously observed failure and a criterion that would fail the repair. Run the candidate through that route. Compare against independent expected output or a known-correct implementation where practical. A deliberately wrong direction, wrong target layer, or stale cache entry makes a good check of a test's sensitivity. Then exercise a neighboring workflow that shares the changed code. This generalizes the requirements-verification matrix practice to one small app team. An issue, code comment or test name can carry that record; a separate tracking system is optional. [NASA Systems Engineering Handbook, Appendix D](https://www.nasa.gov/reference/appendix-d-requirements-verification-matrix/)

### Four decisions, each supported by different evidence

| Decision | Evidence that supports it | What to do when one observation is missing |
|---|---|---|
| Is this implementation worth integrating? | Failure explained at a specific input/state boundary; the current change fixes it on a credible reproduction; its neighbor passes; migrations and exports survive; normal repo checks pass at the intended revision. | Investigate the failing layer, narrow the change or repair it. Codex owns implementation, refactoring, branching and merge decisions within the authorized repo. |
| Does this phone build answer a useful question? | A meaningful repair is present. Build identity and installation path are verified. Known reproducible failures in the intended journey have been worked through. One brief phone exercise will answer something engineering cannot yet establish. | Continue independent engineering. If the sole discriminator is the owner's codec, OEM picker or gesture behavior, say exactly what remains device-specific and why one install is useful. |
| Is a workspace complete? | Its agreed feature inventory is covered through ordinary use, edge cases, performance, save/reopen, external output and physical use. Known failures affecting that workspace are resolved or a change in scope was explicitly accepted. | Keep the affected capability open and advance the next accessible item. Only the owner declares the formal pre-Video locks. |
| Is the app ready for a public release? | All five modes meet their agreed end-to-end requirements, physical evidence covers the supported device range, release signing/update and store package are verified, and final bilingual and agreement flows pass. | Keep the public-release decision separate from engineering milestones and QA distribution. Product acceptance belongs to the owner. |

A file can decode correctly while the interface freezes. A finger gesture can work on one phone while Android 10 exports half a crop. Record which statement each observation supports. When there is a known failure that affects the result you are about to call complete, follow through on it. A progress update can be sent while the next diagnostic, repair or CI run is already under way.

## From a red run to an engineering decision

| Observation | Good next experiment | Mistake this avoids |
|---|---|---|
| Instrumentation does not compile | Read the first compiler error, check the project's installed test APIs/imports, compile the test target and rerun it. | Changing the production renderer to silence an error in test setup. |
| The test reads a dark pixel, but the decoded source moves | Overlay the fitted media bounds on a debug capture, identify where the point lands, then probe moving content at mapped coordinates. Keep the motion and timing checks. | Relaxing a color tolerance until a letterbox gutter passes. |
| A real handset still freezes, synthetic media works | Compare orientation, variable timestamps, keyframe spacing, selected output size, codec route, warm/cold state and edits. Reproduce locally with a rights-cleared reduced case. Record whether UI, clock, decoder or presented image stalls first. | Asking the owner to repeat the same generic test, or dismissing the only failing device. |
| Export becomes fast but looks wrong in the middle | Decode every frame for a short deterministic file and compare a stable marker, delays, order and dimensions. Inspect cache reuse on duplicates and reverse windows. | Improving time by losing motion, reducing resolution or changing the edit. |
| Brush looks right after lift but wrong during touch | Capture with pointer held, both below a partly transparent upper layer and over an unoccluded patch. Compare held, committed, reopened and exported pixels in a common space. | Treating a topmost path overlay as successful layer compositing. |
| Test passes after an unexplained retry | Retain the failing receipt. Reproduce under the triggering timing/order and add deliberate supersession, delayed decode or cancellation as relevant. | Turning an intermittent data race into a green badge. |
| Old projects open but look different | Compare against a preserved legacy fixture and independent expected image, inspect fields before/after save, and test restoring a damaged latest revision. | Silently dropping legacy layers, masks, orientation or source identity. |

If keeping work in separate PRs makes a failure easier to isolate, keep them separate. If one job requires a shared renderer or model repair, change it and verify every consumer it actually affects. When a parent PR lands, check the child base, tree, diff and run identities again. A red child does not invalidate a previously demonstrated property of the parent. A green parent does not qualify its child's new controls.

## Performance is observed at the phone

Use the same input, edit sequence, aspect, output dimensions, quality, palette, duration, device, build type, and storage provider when comparing an optimization. Pin the start and stop events. Distinguish “button tapped to first correct picture,” “continuous play to end,” “Save to file readable by another app” and “project reopened.” Count actual input frames, source seeks, rendered frames and completed writes. Measure warm and cold paths separately. Repeat with alternating build order to expose warm cache and thermal effects. Record individual times; the median of a few trials and worst observed stall are useful. Tail-percentile claims need enough events to support them. Record any changed measurement definition beside the result.

Use the app's existing local traces and Android tooling before adding instrumentation. Prefer timings, frame signatures, stage names and resource counts with synthetic media; keep private filenames, images, audio and URIs out of traces. A trace should answer a question such as “does address-space growth follow each reopen?” or “does the finger wait on a decode on the main thread?” Measure event-to-presentation, work on the UI thread, peak decoded memory and repeated-open recovery. A 60 Hz display offers about 16.7 ms per refresh. A 10 fps GIF may intentionally change pictures only every 100 ms even while controls respond at display refresh rate. A separate UI frame budget and media presentation clock prevent a misleading diagnosis. [Android slow rendering](https://developer.android.com/topic/performance/issues/render) · [Android Macrobenchmark](https://developer.android.com/topic/performance/benchmarking/macrobenchmark-overview)

Suggested collection set: the two emulator lanes in the reviewed runs are API 29 and API 35; add a real API-appropriate low-memory or slower phone, a representative everyday phone and a newer phone where available. Include a landscape or large-screen pass where hit geometry changes. Record model, OS, screen refresh, test variant, whether charging, thermal state, data provider and class of media. Report actual coverage. Emulators are valuable for repeatability, physical devices for touch, codec, thermal and OS integration behavior. Device availability affects the confidence of a claim. It need not halt unrelated fixes.

## A sensible path through the remaining product

| Outcome | Depends on | What unlocks the next piece |
|---|---|---|
| Usable GIF repair and reliable live photo tools | Current branches, historical failing media/fixtures, observable output | One combined build where the actual editor plays the edited result, the file independently plays, and a user can see live edits on the correct layer. The short phone task targets remaining device uncertainty. |
| Deep, trustworthy pre-Video workspaces | Stable geometry, state, history, safe local storage, renderer and source identity | Regular develop engine → verified RAW/color/optics → catalog and batch. Pro layer and selection core → manual subject/retouch/warp → complete saved constructions. GIF correctness → range of real inputs and long exports. Collage core and 20-tile round trips protect each change. Stickers resume after immediate repair work. These paths can advance in parallel where dependencies allow. |
| Four owner-accepted workspaces | The complete promised feature inventory including deferred work, real phones, accessible first-use tasks, actual exports | Explicit formal lock of Regular, Pro, Collage and GIF. Stable shared rendering and decoding work already needed by the four editors can be reused later. |
| Studio Video | Four formal locks | Timeline and deterministic clip mapping → independent local audio and splice → effects, moving regions and color → demanding multiclip export, persistence and physical performance. See the worked example in chapter 03. |
| Full public product | All editing systems built and tested | Final English/Spanish UX and agreements, verified production install/update, final physical qualification, owner release decision. |

## What the owner should receive

Give the owner one meaningful phone build when it can answer an identified question. A directly downloadable **APK**, labeled with version and exact build, is the least ambiguous deliverable. If GitHub returns an Actions ZIP that needs authentication, identify it as such and provide the extracted APK through an authorized delivery path. Verify the file presented to the owner matches the tested artifact, including SHA-256, Android manifest version/package and signing certificate. Examine the previous package/signature before promising side-by-side installation or an in-place update. If tests evaluated a PR tree and a merge moved it, establish tree equality or rerun the changed product. A nearby commit or matching marketing version is insufficient.

An efficient candidate note could read: “This build targets the freeze **after** you trim and apply a Look. We ran your edit sequence through to the end and decoded the saved GIF. On your phone, open your usual clip, apply your usual edit, tap Play and watch through the end. If it stalls, tell us the last moving moment and whether dragging still changes the picture. Your saved project remains available for the next attempt.” Use this wording only when those observations have been performed and preservation has been established. The engineer owns the extended matrix. The owner should get the one observation their handset can uniquely provide.

A final engineering receipt names the build, condition, before/after, remaining device-specific unknown, links to the exact runs and artifact, and the next action already under way. If a release blocker is reproducible, the next action is to fix and rerun it. The owner should not have to say “continue” to get that work done.
