# Verification matrix for real editing sessions

Each row is a compact experiment. The first column gives the question worth answering. The third gives an independently observable result. These rows are a starting inventory, not a request to build a parallel QA system. Put additional cases next to existing repo tests when they reveal a failure the suite would otherwise miss. Checkpoint results apply only to their cited builds. The unexecuted experiments here are proposed evidence, with no implied pass.

### Three different ways a result can be wrong

*The operation reached the wrong object.* Give two tiles the same source or two layers the same name. Use independent stable identities to establish which may change. Verify the other object by reading its saved data and rendering its output.

*The operation was right only on screen.* An overlay, stale thumbnail or proxy can look perfect. Recover the saved project in a fresh process; open the exported file with a separate decoder and compare visible pixels, timings, alpha or audio. For a creative operation with no unique reference image, define a small exact invariant and pair it with a human review of the intended result.

*The operation was technically right but unusable.* Record retries, wait time and where the person lost their place. A 40 dp crop box with four overlapping targets and a render path that updates only after finger-up are both examples. Measure the action where the person experiences it. Disclose which fixture, device and build produced each observation.
