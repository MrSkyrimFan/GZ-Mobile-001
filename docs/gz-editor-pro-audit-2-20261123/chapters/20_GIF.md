## GIF-01 · High · Saving an open GIF project can replace another project

**Trigger.** Start with two existing projects containing different media. In a single video-GIF session, save as A. Open saved project B, change an obvious property such as Reverse, then open Save project. The dialog still contains A. Tapping Save writes B's recipe under A's name. The dialog displays the stale name. A separately chosen source C can trigger the same sequence. In the legacy photo-sequence editor reachable through an existing photo-sequence save, the parallel `fileName` has the same behavior when opening another photo-sequence project. The store's AtomicFile write protects against interrupted writes. It faithfully replaces the file for the supplied key. ## GIF-04 · Medium · Original aspect assumes square video samples

GZ's video import reads width, height and rotation. The stored clip has no sample aspect ratio. At Original aspect the export dimensions use width divided by height. The GIF writer emits an unspecified pixel-aspect field. A platform returning coded dimensions for anamorphic media can therefore place the pixels on a square-pixel raster with the wrong shape. The cited AOSP retriever obtains its video size from the track width/height. Android's MediaExtractor documentation gives the display geometry formula including crop and pixel aspect. OEM outputs may differ, so record the actual values on each emulator and phone. [Import](https://github.com/MrSkyrimFan/GZ-Mobile-001/blob/14df73926c6f7063a488f84e367268168e8e5444/app/src/main/java/com/greenezone/gzphotoeditor/editor/VideoGifSource.kt#L153-L169) · [Dimension calculation](https://github.com/MrSkyrimFan/GZ-Mobile-001/blob/14df73926c6f7063a488f84e367268168e8e5444/app/src/main/java/com/greenezone/gzphotoeditor/editor/GifModel.kt#L41-L55) · [GIF descriptor](https://github.com/MrSkyrimFan/GZ-Mobile-001/blob/14df73926c6f7063a488f84e367268168e8e5444/app/src/main/java/com/greenezone/gzphotoeditor/editor/GifEncoder.kt#L138-L151) · [Android MediaExtractor](https://developer.android.com/reference/android/media/MediaExtractor) · [AOSP retriever](https://android.googlesource.com/platform/frameworks/av/+/c9c96118378c52edeb4c9fb4259813f330e27397/media/libmediaplayerservice/StagefrightMetadataRetriever.cpp) · [FFmpeg display geometry](https://ffmpeg.org/ffmpeg-filters.html#setdar_002c-setsar)

**Known-answer sources.** The two MP4s in `proofs/gif_inputs/` contain the same moving round white marker for 24 frames at 12 fps. One stores 256×144 at 1:1 sample aspect. The other stores 180×144 at 64:45. FFprobe measured a 16:9 display aspect for both. With Small, Original aspect, no crop, no look and normal direction, both should produce 320×180. Coded-dimension math predicts 320×256 for the second. Inspect both the canvas header and the marker because an output container can have the right size and still contain a squashed image. The supplied checker accepted a synthetic correct export and rejected a 320×256 control. No Android result is claimed for these fixtures.

**Repair and proof.** Keep coded geometry for decoder allocations. Derive display geometry from crop, SAR and rotation once, and track whether the retriever has already applied a display transform. Exercise paused, edited-codec, source-native, exported and reopened views. Check on API 29 and API 35 when the optional metadata is present and absent. Preserve old project geometry by default and reconcile metadata carefully on relink. To verify a Small forward Android export, run `python proofs/gif_check_display_aspect.py actual.gif`. The checker uses Pillow. The optional generator `gif_aspect_fixture.py` uses ffmpeg and ffprobe.

## GIF-05 · Low · A long hold can grow by 90 ms when GZ reopens its own edited export

The 66-byte `proofs/gif_inputs/gif_long_hold.gif` contains two unique images. Its red hold is 327,680 ms, followed by blue for 100 ms. Select 50% speed with source timing, save, then open the saved output. The schedule requires red for 655,360 ms and blue for 200 ms. The encoder splits the first hold at 65,535 hundredths, leaving a one-hundredth fragment. GZ's own reader expands a delay less than two hundredths to 100 ms. The file's literal delays are correct, but the reopened GZ timeline adds 90 ms to red. The source is valid, the edited output is small, and the calculation does not depend on an OEM codec. This boundary case arose from the source and independent controls. [Schedule](https://github.com/MrSkyrimFan/GZ-Mobile-001/blob/14df73926c6f7063a488f84e367268168e8e5444/app/src/main/java/com/greenezone/gzphotoeditor/editor/VideoGifSource.kt#L80-L116) · [Writer split](https://github.com/MrSkyrimFan/GZ-Mobile-001/blob/14df73926c6f7063a488f84e367268168e8e5444/app/src/main/java/com/greenezone/gzphotoeditor/editor/GifEncoder.kt#L172-L182) · [Reader clamp](https://github.com/MrSkyrimFan/GZ-Mobile-001/blob/14df73926c6f7063a488f84e367268168e8e5444/app/src/main/java/com/greenezone/gzphotoeditor/editor/GifSourceMetadata.kt#L63-L70) · [GIF89a §23, Graphic Control Extension](https://www.w3.org/Graphics/GIF/spec-gif89a.txt)

**Repair and proof.** When a split would leave one tick, borrowing one tick from the previous fragment yields 65,534 + 2 with exactly the same total. Check totals around 65,535 and multiples thereof. Independently group adjacent images by their actual color so the test permits equivalent encodings. The checker accepted a 65,534+2 control and rejected a 65,535+1 control. No test needs to wait eleven minutes. Run `python proofs/gif_hold_fixture.py check edited-at-50-percent.gif`, parse the encoded output and compare GZ's reopened schedule including its total. This is separate from the common portrait playback freeze.
